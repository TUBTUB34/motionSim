# UR Motion Studio upgrade, 2026-11-12

This is a whole-program pass to make the app ready for company use. The look
follows the reference screenshots in `assets/Screenshots of what i want/`.
Screenshots of the result are in [screenshots-2026-11-12/](screenshots-2026-11-12/).

## What changed for users

| Area | Change |
| --- | --- |
| Window and navigation | The window opens maximized, and **F11** toggles full screen. Text tabs across the top show the current page with an accent underline. A status bar at the bottom shows the connection dot and robot, the Dark mode switch and the app name. |
| **Live monitor** (new, Ctrl+7) | Rolling charts of position, velocity, current, torque and temperature for chosen joints (actual and target). Includes a 3D robot, state tiles and a joint table. **Record → Stop → Save** writes a flight-report ZIP that Flight reports opens like any robot recording. |
| Flight reports | Rebuilt to match the reference. **Left:** the replayed robot, with target overlay and TCP trail; **Protective stop evidence** (pick a stop to jump to it and see the recorded values around it); Joint values; Recording details. **Right:** reading tabs, legend chips, state band (safety, robot or program), Chart and X-axis selectors, a boxed and labelled stop onset, ← + − → zoom, Degrees, and the synchronized script. |
| Backups | **Complete backup** or **Selected items only**, with any combination of Programs, Apps, Logs (`.txt` and `.bak`) and Flight reports. Download progress shows a percentage. |
| Mounting | The installation's mounting angles now orient the robot in every view: live simulator, Live monitor, separate simulator, the Flight reports robot and full-size playback. Recordings read their own `files/*.installation`. Live recordings store the pulled installation's mounting, TCP and payload. |
| PDF reports | The flight PDF is now a real **Flight Recording Report**. All three reports share a consistent page frame. See [reports/report-audit-2026-11-12](../reports/report-audit-2026-11-12/README.md). |

| RTDE | The client requests 125 Hz instead of 30 Hz, plus target position, velocity, acceleration, current and torque. It stays read-only. |

## Mounting correction and final visual review

The final mounting correction uses `Rx(-tilt) @ Rz(-base)` for PolyScope's
saved `WorldtoMarshal` angles. The previous positive signs mirrored the
180°/45° installation. The regression test checks the three observed mounting
configurations against the `set_gravity()` values from real programs; a separate
read-only check passed for all 16 locally available recordings. Gravity verifies
the direction of world up, but does not determine yaw about world vertical.

Recorded playback defaults to **World (mounting)**. README and in-app help now
describe that default and the optional TCP and Robot base views consistently.
The remaining Simulator setup, Logs, Reports, Checklist and retrieval pages were
captured and reviewed in both themes. See the
[screenshot index](screenshots-2026-11-12/README.md) and
[mounting receipt](../reports/completion-2026-11-12/mounting-check.json).

## Follow-up, 2026-11-13: Windows sizing and mounting adjustment

**Windows sizing.** On a display scaled to 175 % the EXE looked 1.75× larger than
under WSL, and blurred. The process was not DPI-aware, so Windows gave it a
1463 × 914 virtual screen and stretched the window; WSL draws one-to-one on the
real 2560 × 1600. `ui_theme.make_root()` now makes the process per-monitor
DPI-aware and keeps Tk at 96 DPI, because the layout is sized in pixels. Control
sizes are unchanged (Home tab 68 × 46 px, 17 px line spacing), now in real pixels.
On a high-resolution display at a large scale, text is therefore as small as it is
under WSL.

**Mounting adjustment.** The Simulator tab and the separate simulator have a
**Mounting** row: − 45° and + 45° for Base and Tilt, as in PolyScope, plus typed
angles and **Use saved**. `view.set_mounting_override()` stores one adjustment per
application and every `RobotView` draws with it (Simulator, separate simulator,
Live monitor, Flight reports), with an amber note in each adjusted view. It lasts
until the app closes and is display only: nothing is written to the robot, the
installation or a recording. Controls are in `mounting_view.py`.

**Model set on connect.** The installation file does not name the robot model, so
`kinematics.identify_models()` compares the streamed joint angles, TCP position and
TCP offset with each model's nominal dimensions, and `SimulatorApp.check_model()`
switches the model when exactly one size fits. On 6,496 poses from the 16 local
recordings (UR10e and UR15) it was right every time: the right model is within
3.9 mm, every other size at least 15 mm away. UR5e/UR7e and UR10e/UR12e share
dimensions; within those pairs the selection is kept.

**RTDE timeout.** Connect and receive now wait 10 s instead of 3 s (`rtde_client.py`).
Not tested, at the user's request.

**Hidden test runs.** UI tests and the EXE smoke test open real windows and take
keyboard focus. `scripts/run_hidden.py <command>` runs a command on a separate,
invisible Windows desktop; `build_windows.bat` uses it for its smoke test. On Linux
use `xvfb-run -a <command>` (Xvfb is not installed on the development PC).

  `dist/URMotionStudio.exe`: 109,067,188 bytes, SHA-256
  `3b0fdd62fb2c73a59af416bce51f219ceef96afeb6407b075bcb71110188be74`.

## Not verified

- **No physical robot was contacted.** Live tests used a loopback RTDE mock. The
  real stream rate depends on the controller, which caps the requested 125 Hz.
- Model detection ran against recordings and a loopback robot, not a live controller.
- The EXE was checked on one PC (2560 × 1600 at 175 %), not on a second monitor
  with a different scale or on a clean machine.
